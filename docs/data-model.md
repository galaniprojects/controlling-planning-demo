# VIPER Data Model Reference

Canonical reference for all SQLAlchemy models in the VIPER Demo App. **70 models across 14 files** in `backend/models/`. Compiled directly from source — the `.py` files are authoritative; this doc is a navigable wrapper. Update this doc in the same commit that changes a model.

## How to read this doc
- **Per-model blocks** list only the *interesting* columns. Boilerplate (`id` PK autoincrement, `created_at`/`modified_at` timestamps) is omitted unless something is special about them.
- **Nullability** (`NOT NULL`) is called out only when notable — by default, follow the SQLAlchemy declaration in source. When in doubt, read the model file directly.
- **Relationships** line covers `back_populates`, cascade behaviour, and disambiguation via `foreign_keys` where multiple FKs target the same table.
- **Notes** call out non-obvious constraints, decision-tag pointers (e.g. `[F-DM-01]`), service-layer invariants, and cross-version lineage.
- **Decision tags** like `[E-04c]` are pointers into the v5/v5.1/v5.2 spec documents. The active spec lives in `guides/`; older spec material is kept in a local-only archive (not tracked in git).

## Architectural conventions

- **SQLAlchemy ORM only** for application code — no raw SQL except `backend/seed/seed.sql`.
- **Soft delete** via `is_active` flag on master-data models — never hard-delete cost centres, people, LoBs, or competence centres.
- **Effective-date rate tables** — `RateTable` carries `previous_rate` + `previous_effective_date` so historical cost calculations use the rate in effect at the time.
- **Server-side computation** — frontend receives ready-to-render data; no roll-ups or calculations client-side.
- **Sparse-edge storage** for graph/matrix data (`Distribution`, `BTCProfileLine`, `UserMeasurement`) — only non-zero/actually-flowing rows are stored; absence = zero.
- **Polymorphism** via discriminator column on `ChargeableEntity` (`entity_type`) and dual-FK on `Allocation` (`project_id` + `chargeable_entity_id`).
- **Snapshot pattern** for immutable history (`ProjectSubmissionSnapshot`, `CRSubmissionSnapshot`, `ForecastSnapshot`, `ProgressSnapshot`, `ForecastVersion`).
- **Versioning** via a `DistributionVersion` effective-dated header FK'd from `Distribution.version_id` / `RollupCache.version_id` (Charging/UM rework FD-3 — production chain resolved by latest `active_from`; scenario-scoped forks via nullable `scenario_id`), a `UMVersion` draft/active header with `(year, quarter, activated_at)` identity (UserMeasurement; active immutable, never updated in place), or sequential per-project numbering (ForecastVersion).
- **Algorithmic WBS** — never stored on the row; generated by `services/wbs_generator.py` per `[F-DM-03]`.
- **Audit categories** — 8-category taxonomy on `AuditLog`; `_log_audit()` requires `category=` keyword-only at every call site.

## Organization (`organization.py`)

### `Location` — `locations`
Workforce location master (Munich, Budapest, Pune). Distinct from `ChargingLocation` — the Cluster F charging-code master.

**Key columns.** `id` String(50) PK, `city`, `country`, `is_active` (soft delete).
**Relationships.** `cost_centers` → CostCenter (back_populates).

### `CompetenceCenter` — `competence_centers`
Cost pool grouping (APD, INF, BSO, DDA).

**Key columns.** `id` String(50) PK, `name`, `is_active`.
**Relationships.** `cost_centers`, `rate_entries`, `people`.

### `CostCenter` — `cost_centers`
Org unit linking workforce location + competence centre.

**Key columns.** `id` String(50) PK, `name`, `location_id` FK → locations, `competence_center_id` FK → competence_centers, `is_active`.
**Relationships.** `location`, `competence_center`, `people`.

### `GroupingEntityType` — `grouping_entity_types`
Type catalogue for the configurable portfolio hierarchy per `[ADM-01]` (e.g. "Line of Business", "Initiative", "Programme").

**Key columns.** `id` String(50) PK, `name`, `is_active`.
**Relationships.** `entities`, `hierarchy_levels`.

### `GroupingEntity` — `grouping_entities`
Node in the configurable portfolio hierarchy. Self-referential tree via `parent_entity_id`.

**Key columns.** `id` String(50) PK, `entity_type_id` FK, `name`, `parent_entity_id` FK → grouping_entities (self-ref), `is_active` (soft delete).
**Relationships.** `entity_type`, `parent` (remote_side), `project_assignments`.
**Notes.** Referenced by `ChargeableEntity.hierarchy_node_id` per `[F-DM-04]` — Cluster F entities use the same hierarchy as projects.

### `GroupingHierarchy` — `grouping_hierarchies`
A named hierarchy definition (e.g. "v5 Default", "Strategic Initiative View"). Multiple hierarchies can exist; one is `is_active_hierarchy=True` at a time.

**Key columns.** `id` String(50) PK, `name`, `is_active_hierarchy` (default False).
**Relationships.** `levels` → GroupingHierarchyLevel (ordered by `level_order`).

### `GroupingHierarchyLevel` — `grouping_hierarchy_levels`
Defines one level of a hierarchy: which `GroupingEntityType` lives at depth `level_order`.

**Key columns.** `id` Integer PK, `hierarchy_id` FK, `level_order`, `entity_type_id` FK.

### `ProjectGroupingAssignment` — `project_grouping_assignments`
Junction linking projects to portfolio grouping entities.

**Key columns.** `id` Integer PK, `project_id` FK → projects, `grouping_entity_id` FK → grouping_entities.

## People (`people.py`)

### `RoleType` — `role_types`
Job role catalogue (e.g. Senior Engineer, Project Manager). Source for `RateTable` rates and `Allocation`/`Forecast` line-item attribution.

**Key columns.** `id` String(50) PK, `name`.
**Relationships.** `people`, `rate_entries`.

### `Person` — `people`
Master-data record for a team member. **Distinct from `User`** — Person is HR-style master data (cost centre, role, capacity); User is system-access identity.

**Key columns.** `id` String(50) PK, `name`, `role_type_id` FK NOT NULL, `cost_center_id` FK (nullable), `competence_center_id` FK (nullable), `is_active`.
**Relationships.** `role_type`, `cost_center`, `competence_center`, `allocations`.
**Notes.** Referenced as FK target by 15+ models (Project's `pl_person_id` and `progress_updated_by_id`, MilestoneDeliverable's `completed_by_id`, ForecastVersion's `created_by_id`, Allocation, ResourceRequest, CapacityActionLog, ChargeableEntity's `responsible_person_id`, ProjectDependency's `created_by_person_id`, etc.). Not every Person is a User; not every User maps to a Person.

### `RateTable` — `rate_table`
Hourly rates by `(role_type, competence_center)` with effective-date validity. Tracks current + previous rate so historical cost calculations apply the rate in effect at the time.

**Key columns.** `id` Integer PK, `role_type_id` FK, `competence_center_id` FK, `hourly_rate` Numeric(10,2), `effective_date` String(10) `YYYY-MM-DD`, `previous_rate` Numeric(10,2) nullable, `previous_effective_date` String(10) nullable.

## Projects (`projects.py`)

### `Project` — `projects`
Central domain entity. Status lifecycle, CapEx/OpEx, Tech Navigator profile, v5 pipeline state, v5.1 progress tracker.

**Key columns (grouped):**

*Core identity & lifecycle:*
- `id` String(50) PK, `name` String(300), `description` Text, `pl_person_id` FK → people (nullable, the Project Lead).
- `review_state` String(30) NULL — intake/submission review sub-state only: `pending_cc_confirmation` | `pending_approval` | `changes_requested` | NULL (not mid-review). **Orthogonal to `pipeline_stage`** (the lifecycle source of truth). Replaced the former overloaded `status` column (retired): the lifecycle values (draft/active/planned/completed/rejected) now live exclusively on `pipeline_stage`; readers use stage-group predicates (`BACKLOG_STAGES`/`EXECUTION_STAGES`/`TERMINAL_STAGES` in `services/pipeline.py`).
- `submission_feedback` Text — controller/CC Owner feedback for the `changes_requested` review_state.
- `rag_status` String(10) — `green` | `amber` | `red` | NULL (pending/draft).
- `capex_opex` String(10) NOT NULL — `capex` | `opex`.
- `start_month` String(7) `YYYY-MM` NOT NULL, `end_month` String(7) (nullable, NULL for services), `projected_end_month` String(7).
- `is_service` Boolean default False, `annual_budget` Numeric(14,2) (services), `total_budget` Numeric(14,2) (baseline).
- `last_forecast_submitted_month` String(7), `is_active` Boolean.

*Tech Navigator profile per `[A-TN-01..09]` (all nullable, populated via `PUT /api/projects/{id}/tech-navigator`):*
- `project_type` Integer (1=business case, 2=strategic, 3=legal/compliance).
- `transformation_level` String(3) (T0 | T1 | T2).
- Three Complexity sub-criteria (1–5): `tn_standardization`, `tn_usage`, `tn_maintenance`.
- Three Value Creation sub-criteria (1–5): `tn_financial_benefit`, `tn_payback`, `tn_competitive_advantage`.
- Two reserved slots (not surfaced in UI): `tn_value_reserved_1`, `tn_value_reserved_2`.
- Denormalised composite scores Numeric(4,2): `complexity_score`, `value_creation_score`, `composite_score` (recomputed on every TN write or admin weight change).
- `tshirt_size` String(2) — XS/S/M/L/XL, derived from `total_budget`. Sub-criterion weights, ranking weights, and t-shirt thresholds live in `PlanningParameter` rows under `param_group='tech_navigator'`.

*v5 Session A2 lifecycle per `[A-PS-01]` `[A-DOI-01]`:*
- `pipeline_stage` String(30) NOT NULL (`server_default='Proposed'`) — **the single lifecycle source of truth** (non-null since the `status`-column retirement). Working stage names per `[A-PS-02]`: `Proposed`, `Under Evaluation`, `Approved`, `Active`, `Hyper-maintenance`, `Completed`, `Run entity spawned`, `Paused`, `Cancelled`. **VIPER §2.3 (Wave 1):** `Operate` and `Retired` retired as project stages (a project never operates/retires — its spawned Run entity does); replaced by the two terminal stages `Completed` (no Run entity) and `Run entity spawned` (handed off, see `run_entity_id`). Seed rows migrated accordingly.
- `doi` Integer (0–5 per `[A-DOI-01]`).
- `frozen_doi` Integer — preserved DoI for off-path stages (Paused/Cancelled) per `[A-PS-03]`.
- `run_entity_id` String FK → `chargeable_entities.id` (nullable, `use_alter=True` to break the `projects ↔ chargeable_entities` create_all cycle) — **VIPER §7 (Wave 1).** Populated only when `pipeline_stage == 'Run entity spawned'`; points to the Offering / Internal Service that now carries the finished project's ongoing cost. Passive relationship `run_entity` (no back-populate — keeps the charging side read-only). **Wave 3 wires the router enforcement** (`POST /api/projects/{id}/pipeline/transition`): a transition to `Run entity spawned` requires a non-null `run_entity_id` (409 otherwise), the target must resolve (404 otherwise) and be an `Offering`/`InternalService`, never a `Project` (409 otherwise).
- `handover_month` String(7) (`YYYY-MM`, nullable) — **VIPER §7 (Wave 3).** Month the project was handed over to its Run entity; set router-side (= current demo month) when the `Run entity spawned` transition is applied. Drives `handover_year` and `cumulative_since_handover` in the project-summary payload (`GET /api/portfolio/projects/{id}/summary`): `cumulative_since_handover = run_entity.annual_cost × max(1, current_fiscal_year − handover_year + 1)` — a demo-grade roll-up that holds annual cost flat and is inclusive of both endpoint years (the span is clamped to ≥ 1 so a future handover month can't produce a zero/negative figure). Null until handover.
- `ai_council_approved` Boolean default False — DoI 0→1 gate per `[A-DOI-03]`.
- `ai_council_doc_url` Text — OneDrive link per `[A-DA-01]`.
- `within_cutoff` Boolean — settable in A2; A3 replaces with computed value from ranking-engine envelope walk per `[A-PS-06]`.

*v5 E1 progress tracker per `[E-04c]` (live-editable via `PATCH /api/projects/{id}/progress`; snapshotted at forecast cycle completion):*
- `current_milestone_id` Integer FK → project_milestones (`use_alter=True`, name `fk_project_current_milestone` to break the create_all cycle). Pointer to currently executing milestone; service derives from demo date when NULL.
- `progress_pct` Numeric(5,2) — intra-milestone 0–100. Auto-computed from current milestone's deliverable checklist when items exist; manually overridable when `progress_pct_manual_override=True` (`server_default="0"`).
- `status_narrative` Text — PL's free-text status (1–2 sentences). Mandatory at forecast cycle submission per `[E-04c]`.
- `next_milestone_confidence` String(20) — `on_track` | `at_risk` | `blocked`. Service layer enforces `confidence_reason` non-empty when `at_risk`/`blocked`.
- `confidence_reason` Text, `progress_updated_at` DateTime, `progress_updated_by_id` FK → people.

**Relationships.** `pl` (foreign_keys=[pl_person_id]); `baselines`, `forecasts`, `actuals`, `allocations`, `change_requests` (back_populates); `milestones` (ordered by sequence_number, foreign_keys disambiguated); `entity_assignments`; `forecast_versions` (ordered by version_number); `progress_snapshots` (ordered by snapshot_at); `current_milestone` (foreign_keys=[current_milestone_id], `post_update=True`).

### `MilestoneType` — `milestone_types`
Global catalogue of milestone types per `[A-BK-34]`. Provides default colour and suggested ordering for the picker UI.

**Key columns.** `id` String(50) PK, `name`, `default_color` String(20), `suggested_ordering` Integer, `is_active`.
**Notes.** Per-milestone colour overrides (`ProjectMilestone.color`) take precedence; fall back to `default_color` when NULL. Read-only via `GET /api/admin/milestone-types`.

### `ProjectMilestone` — `project_milestones`
Project milestones with baseline + forecast date ranges per `[A-MS-01]`. Renamed from `ProjectPhase` (table `project_phases`) for terminology consistency.

**Key columns.** `id` Integer PK, `project_id` FK NOT NULL, `sequence_number` Integer NOT NULL, `name` String(100), `milestone_type_id` FK (nullable), `baseline_start`/`baseline_end`/`forecast_start`/`forecast_end` String(7) `YYYY-MM` NOT NULL, `color` String(20) (per-milestone override), `baseline_locked_at` DateTime (nullable, set on first save).

**Relationships.** `project` (back_populates), `milestone_type`, `deliverables` (ordered by sequence, `cascade="all, delete-orphan"`).

**Notes.** Baseline dates immutable after first lock except via controller override with audit log entry per `[A-MS-03]`.

### `MilestoneDeliverable` — `milestone_deliverables`
Per-milestone deliverable checklist item per `[E-04c]`. Max 10 items per milestone, enforced at service layer via `services/progress_tracker.MAX_CHECKLIST_ITEMS`.

**Key columns.** `id` Integer PK, `milestone_id` FK `ondelete="CASCADE"`, `sequence` Integer NOT NULL, `text` Text NOT NULL, `is_complete` Boolean (`server_default="0"`), `completed_at` DateTime, `completed_by_id` FK → people.

**Relationships.** `milestone` (back_populates).

**Notes.** When deliverables exist on the current milestone, `Project.progress_pct` auto-computes from completion ratio; PL retains manual override flag. Sequence is contiguous (1..N); service-layer reorder not implemented in E1.

### `ProgressSnapshot` — `progress_snapshots`
Versioned snapshot of project progress at forecast cycle completion per `[E-04c]`. Created by `services/progress_tracker.capture_progress_for_cycle` alongside Cluster C1's `capture_versions_for_cycle`.

**Key columns.** `id` Integer PK, `project_id` FK NOT NULL, `cycle_label` String(50), `cycle_id` String(20) (links to `ForecastCycleState.cycle_id`), `snapshot_at` DateTime NOT NULL default utcnow, `created_by_id` FK → people. Plus denormalised progress state: `current_milestone_id`/`name`/`sequence`, `progress_pct`, `progress_pct_manual_override`, `status_narrative`, `next_milestone_confidence`, `confidence_reason`, `checklist_payload_json` Text (full deliverable checklist as JSON keyed by milestone_id, for history-without-FK-walks).

**Relationships.** `project` (back_populates).

**Notes.** Best-effort fan-out — failure does not block forecast cycle submission.

### `ProjectDependency` — `project_dependencies`
Inter-project dependency edge per `[D-AC-05]`. **Soft constraint** — graph is presented as warning surface; cycle detection per `[D-AC-08]` flags problems on save but does not block transitions.

**Key columns.** `id` Integer PK, `predecessor_project_id` FK NOT NULL, `successor_project_id` FK NOT NULL, `dependency_type` String(30) (catalogue per `[D-CAT-03]`: `finish_to_start` | `start_to_start` | `finish_to_finish` | `start_to_finish`; D1 accepts any string), `lag_days` Integer (nullable lag/lead), `notes` Text, `created_by_person_id` FK → people.

**Relationships.** `predecessor`, `successor` — both FK-disambiguated since both target `projects.id`.

## Financials (`financial.py`)

### `ExternalCostType` — `external_cost_types`
Cost categories (Consulting, Cloud-Infrastructure, Licenses, Hardware, Other). Admin-managed per `[E-08e]` `[E-08f]` via `/api/admin/external-cost-types`.

**Key columns.** `id` String(50) PK, `name`.

### `Baseline` — `baselines`
Immutable approved plan — one row per project × month × line item.

**Key columns.** `id` Integer PK, `project_id` FK NOT NULL, `month` String(7) NOT NULL, `category` String(20) NOT NULL (`internal` | `external`), `sub_category` String(50) NOT NULL (role_type_id or cost_type_id), `hours` Numeric(10,2) (internal only), `amount_eur` Numeric(14,2) NOT NULL, `description` String(200) (external line-item), `capex_opex` String(10) (per-line CapEx/OpEx), `vendor` String(200), `ext_status` String(30), `role_type_id` FK → role_types (nullable; v5.1 `[C-07]` optional role attribution for external consulting/leased-staff items, always NULL for `category='internal'`).

**Notes.** Role attribution enables F&P grid `[Category] — [Role Name]` labels.

### `Forecast` — `forecasts`
Living plan updated via approved CRs. Mixed-granularity per `[C-FV-01]`.

**Key columns.** Same shape as `Baseline` plus:
- `is_provisional` Boolean (`server_default="0"`) — `True` for cells beyond granularity boundary (outer zone per `[C-FG-07]`). Manual CR writes clear this flag.
- *External-cost procurement tracking (v5.1 `[C-09]`, all nullable, only for `category='external'`):* `po_number` String(50), `vendor`, `ext_status`, `po_amount` Numeric(14,2) (`server_default="0"`, monthly committed PO obligation), `accrual_amount` Numeric(14,2) (`server_default="0"`, monthly accrual estimate), `contract_end_month` String(7) (denormalised line-level metadata).

### `Actuals` — `actuals`
Read-only historical spend (from SAP/CATS).

**Key columns.** Same shape as `Baseline` plus:
- `po_number` String(50) — v5.1 `[C-09]` mirrors `Forecast.po_number` so `open_po` reconciles per `(vendor, po_number)` pair.
- `invoiced_amount` Numeric(14,2) (`server_default="0"`) — v5.1 `[C-09]` subset of `amount_eur` actually invoiced (vs. only goods-received). Drives the **Remaining Not Invoiced** KPI.
- `role_type_id` FK → role_types (nullable; v5.1 `[C-07]` same semantics as Baseline).

### `ForecastVersion` — `forecast_versions`
Immutable point-in-time snapshot of a project forecast per `[C-FV-01..07]`.

**Key columns.** `id` Integer PK, `project_id` FK NOT NULL, `version_number` Integer NOT NULL (sequential per project), `version_type` String(20) (`cycle` | `cr_approval`; legacy `manual` still accepted for historic rows), `cycle_label` String(50), `cycle_id` String(20), `change_request_id` FK → change_requests (NULL for cycle), `created_at` DateTime NOT NULL default utcnow, `created_by_id` FK → people NOT NULL, `granularity_boundary_months` Integer default 12, `planning_horizon_months` Integer default 60, `payload_json` Text (full grid as JSON, schema_version 1, ~70 KB/version per `[C-FV-07]`), `cell_count` Integer / `total_amount_eur` Numeric(14,2) (denormalised stats for fast list queries).

**Constraints.** `UniqueConstraint(project_id, version_number, name="uq_fv_project_version")` per `[C-FV-04]`.

**Relationships.** `project` (back_populates), `created_by` (foreign_keys=[created_by_id]).

**Notes.** Created automatically: on CR approval (6-line try-wrapped hook in `approve_cr` per `[C-FV-02]`); on cycle completion (fan-out to all active projects per `[C-FV-05]`). The controller-triggered manual snapshot path (`version_type='manual'` per `[C-FV-03]`) was removed; the column still accepts the literal so any pre-existing rows remain readable, but no new manual versions are created. **NOT replacing** `ForecastSnapshot` (kept for accuracy report).

### `ExternalCostDelivery` — `external_cost_deliveries`
v5.1 `[C-09]` row-expansion content for the External Costs monthly grid. One row per scheduled delivery milestone, keyed implicitly by `(project_id, vendor, po_number)`.

**Key columns.** `id` Integer PK, `project_id` FK, `vendor`, `po_number`, `sub_category` FK → external_cost_types (nullable), `milestone_name` String(100), `expected_month` String(7), `expected_amount` Numeric(14,2), `delivered_month` String(7) (NULL = not yet delivered).

**Notes.** Loaded only on row-expansion path; not part of base grid query.

### `ExternalCostInvoice` — `external_cost_invoices`
v5.1 `[C-09]` row-expansion content. One row per invoice received against an external-cost PO line.

**Key columns.** `id` Integer PK, `project_id` FK, `vendor`, `po_number`, `invoice_number` String(50) NOT NULL, `invoice_date` Date NOT NULL, `amount` Numeric(14,2) NOT NULL, `status` String(20) (`received` | `paid`).

### External cost status vocabulary (v5.1 `[C-09]`)

`Forecast.ext_status` / `Baseline.ext_status` / `Actuals.ext_status` use the 6-value lifecycle set:

| Status | Meaning |
|---|---|
| `planned` | Forecasted, no PO yet |
| `ordered` | PO issued, goods/services not yet delivered |
| `goods_received` | Delivered/performed, invoice not yet received |
| `invoiced` | Invoice received |
| `accrual` | Cost recognised, invoice pending |
| `open` | Partial-PO-fulfillment marker (Wave 5 seed top-up) |

Mirrored in `frontend/src/types/api.ts::ExternalCostStatus` and `backend/schemas/external_costs.py::ExternalCostStatus`. The frontend `ExternalCostStatusBadge` component owns the visual mapping. Wave 5 remap (`accrued`→`accrual`, `committed`→`ordered`, `delivered`→`goods_received`, `requested`→`planned`) was a one-time seed sed.

## Change Management (`change_requests.py`)

### `ChangeRequest` — `change_requests`
Two-stage approval workflow: CC Owner confirmation → Controller approval.

**Key columns.** `id` Integer PK, `project_id` FK NOT NULL, `submitted_by_id` FK → people NOT NULL, `submission_timestamp` DateTime NOT NULL, `status` String(30) NOT NULL (`draft` | `pending_cc_confirmation` | `sent_back_by_cc` | `pending_controller_approval` | `sent_back_by_controller` | `approved` | `rejected`), `change_category` String(20) (`scope` | `timeline` | `resource` | `external_cost` | `other`), `summary` String(500) NOT NULL, `justification` Text, `is_system_suggested` Boolean default False.

*Stage 1 — CC Owner confirmation:* `cc_owner_id` FK, `cc_confirmation_timestamp`, `cc_status` String(20) (`pending` | `confirmed` | `declined`), `cc_comments` Text.

*Stage 2 — Controller approval:* `controller_id` FK, `controller_approval_timestamp`, `controller_status` String(20) (`pending` | `approved` | `rejected` | `sent_back`), `controller_comments`, `controller_feedback`.

### `UMVersion` — `um_versions`

**Indexes.** `ix_um_versions_yq_status` (`year, quarter, status`) — drives the active-version resolver.

**Relationships.** `cells` → `UserMeasurement` (`back_populates`, `cascade="all, delete-orphan"`); `copied_from` self-ref (`remote_side`).

### `DistributionVersion` — `distribution_versions`
Effective-dated Stage 1 distribution version header per `[F-S1-02..04]` (Charging/UM rework cluster FD-3). Replaces the v4 row-column ``version`` string (`baseline` | `forecast` | `actuals` | `scenario-<id>`) with a first-class header. Cadence-agnostic — there is ONE global production chain (no year scope on versions or edges); the year axis lives on the cost being distributed. Mirrors the `UMVersion` / `BTCProfile` draft→active lifecycle: draft is editable, active is frozen and immutable, `activated_at` is the freeze timestamp.

**Key columns.** `id` Integer PK, `active_from` Date NULL (drives the production resolver — required at activate for production, NULL for drafts and scenario versions), `status` String(10) NOT NULL default `draft` / `server_default='draft'` (`draft` | `active` per `DISTRIBUTION_VERSION_STATUSES`), `rationale` Text NOT NULL default `''` (`[F-S1-05]` version-level rationale — empty allowed in draft; service requires non-empty on activate), `origin` String(20) NOT NULL (`blank` | `copy_active` | `copy_prior` | `seed` per `DISTRIBUTION_VERSION_SOURCES`/`[F-S1-04]`), `copied_from_version_id` FK → distribution_versions (`ondelete=SET NULL`; provenance for `origin='copy_active'`/`'copy_prior'`, mirrors `UMVersion.copied_from_version_id`), `scenario_id` FK → scenarios (`ondelete=CASCADE`; NULL = production, non-NULL = scenario-scoped lever-12 fork), `created_at`, `created_by_person_id` FK → people, `activated_at` DateTime NULL (set on activate; immutable thereafter; NULL = draft).

**Constraints.** `CheckConstraint(status IN ('draft','active'), name="ck_distribution_version_status")`, `CheckConstraint(origin IN ('blank','copy_active','copy_prior','seed'), name="ck_distribution_version_origin")`. **No** DB-level uniqueness on `active_from` — service-enforced (same pattern UMVersion uses; SQLite partial unique indexes are not portable here): (a) two production active rows must not share `active_from`; (b) active production version is immutable (header + edges); (c) activation requires non-NULL `active_from` and non-empty `rationale`; (d) `status='active'` requires `scenario_id IS NULL` — scenario versions stay `'draft'` permanently.

**Indexes.** `ix_distribution_versions_status_active_from` (`status, active_from`) — drives the production resolver; `ix_distribution_versions_scenario` (`scenario_id`) — drives lever-12 cleanup; `ix_distribution_versions_copied_from` (`copied_from_version_id`) — lineage queries.

**Relationships.** `edges` → `Distribution` (`back_populates`, `cascade="all, delete-orphan"`); `copied_from` self-ref (`remote_side`).

**Resolution rule (production only).** `SELECT * FROM distribution_versions WHERE scenario_id IS NULL AND status='active' AND active_from <= :evaluated_date ORDER BY active_from DESC LIMIT 1`. `:evaluated_date` is the runtime-computed current period (`config.get_current_period()`, see "Temporal anchor" in Cross-cutting patterns); the seed needs ≥1 production version with `active_from` on/before the canonical anchor (`2026-04`, shifted forward at load).

**Lever-12 mapping.** One `DistributionVersion` per scenario (`scenario_id=N`, eager-created on first mutation, `status='draft'` permanently, `origin='blank'`, `active_from=NULL`). Anchor edges copy into it as the user touches sources (lazy-fork preserved at edge level). Union-aware reads: for each source entity, scenario edge wins if it exists; else fall back to anchor production version's edges. Anchor pinned at scenario creation via `Scenario.anchor_distribution_version_id` so production reactivations don't shift impact deltas mid-flight. Cleanup on scenario delete cascades from `scenarios → distribution_versions(scenario_id=N) → distributions(version_id=…)`.

### `Distribution` — `distributions`
Stage 1 inter-service distribution edge per `[F-S1-01..05]`. Sparse storage — one row per actually-flowing edge per `DistributionVersion`. **The "To Business" share is *not* an edge** — lives on `ChargeableEntity.to_business_pct` per `[F-DM-02]`. Self-retained percentage is derived: `100 − to_business_pct − Σ(distribution %)`. Cadence-agnostic per the FD-3 rework — no `year` column on edges; the year axis lives on the cost being distributed.

**Key columns.** `id` Integer PK, `version_id` FK → distribution_versions NOT NULL (`ondelete=CASCADE`), `source_entity_id` FK NOT NULL, `destination_entity_id` FK NOT NULL, `percentage` Numeric(5,2) NOT NULL, `rationale` Text NULL (per-edge rationale per `[F-S1-05]` — UI nudges on % change vs the copied baseline; surfaces in diff report; optional because per-edge rationale is per-change context, not contractual — the required field is the version-level `DistributionVersion.rationale`), `chain_depth` Integer NULL (cache of the longest root-to-leaf path length passing through this edge, in its version; Service Workbench Session 1; bulk-recomputed after every edge mutation in the same version; NULL = unwritten cache (seeded edges, never-mutated versions); first edge write in any version populates the column for all edges in that version; powers the depth badge in the entity picker without per-request graph walks).

**Constraints.**
- `UniqueConstraint(version_id, source_entity_id, destination_entity_id, name="uq_distribution_edge")` — same edge can carry different percentages across versions.
- `CheckConstraint("source_entity_id <> destination_entity_id", name="ck_distribution_no_self_loop")`.
- `CheckConstraint("percentage >= 0 AND percentage <= 100", name="ck_distribution_pct_range")`.

**Indexes.** `ix_distributions_version_source` (version_id, source); `ix_distributions_version_dest` (version_id, dest).

**Relationships.** `version` → `DistributionVersion` (`back_populates="edges"`); `source_entity` (foreign_keys=[source_entity_id], back_populates="outgoing_edges"); `destination_entity` (foreign_keys=[destination_entity_id], back_populates="incoming_edges").

**Notes.** Sum-rule per `[F-S1-02]`: `to_business_pct + Σ(distribute %) ≤ 100`; residual is derived as self-retained. Cycle detection per `[F-S1-05]` is hard-block on save with the cycle chain returned in the 409 body for UI rendering. DAG resolution lives in `services/dag_resolver.py::compute_effective_cost`; cycles are caught at edge-save by `detect_cycle_db`, so the resolver uses memoization (full `EffectiveCostResult` cache keyed by entity_id, Service Workbench Session 1) — no cycle-breaking skip-set inside the recursion. `get_upstream_chain` returns all upstream paths for the rollup drill-down per `[F-RV-04]` with `max_depth` resolved from `PlanningParameter.max_allocation_depth` (default 6) when unspecified. Depth is a third save-time validation alongside cycle + sum-rule; violating-path returned in the 409 body. Edits are scoped to a **draft** version — active production versions are immutable per `[F-S1-08]` (service-enforced).

### Lever 12 sandbox storage pattern (Scenario integration)

Stage 1 distribution edges fork into a dedicated scenario `DistributionVersion` (`scenario_id=N`, `status='draft'`, `origin='blank'`, `active_from=NULL`) on first mutation per `[F-S1-04]`; the anchor production version's rows are never touched. The anchor version is pinned at scenario creation via `Scenario.anchor_distribution_version_id` so subsequent production reactivations do not shift impact deltas mid-flight (NULL = legacy fallback: resolve by `evaluated_date` at read time). Stage 2 BTC line and `to_business_pct` mutations live as `ScenarioAction` overlays (live `BTCProfile`/`BTCProfileLine` rows untouched) and are applied at impact-calc time. Promote materialises overlays onto canonical rows. Cleanup on scenario delete cascades from `scenarios → distribution_versions(scenario_id=N) → distributions(version_id=…)` via the FK `ondelete=CASCADE` (simpler than the v4 "delete all rows where version like 'scenario-%'" pattern). Cycle detection is union-aware (anchor + scenario versions). Promote permission per `[F-AC-01]`: controllers always allowed; other roles require an explicit `RolePermissionGrant` row for the relevant `entity_type` (`btc_profile` or `distribution`).

### Project-Scope Redesign — Layer-2 hand-edit overlay (Simulator spec §5)

The project-scope redesign stores a scenario's edits in two layers. **Layer 1 (macros)** reuses `ScenarioAction` rows (`scope='project'`, `action_type ∈ PROJECT_MACRO_ACTION_TYPES` = `delay_project` | `accelerate_project` | `pause_project` | `remove_project`) as ordered transforms re-derivable against a rebased anchor — no new table. **Layer 2 (hand edits)** is the sparse overlay below: keyed by (project, line, month) for cell values, with companion rows for added/removed lines, mix changes, and plan edits. The overlay *is* the plan-delta the promote / apply diff consumes directly (spec §6) — it is never replayed as a coarse action. Resolution order (spec §5.1): anchor → apply macros in order → overlay hand edits on top, hand-edits-win, absolute-month keying (§5.2). Module-level vocab constants in `scenarios.py`: `OVERLAY_CELL_FIELDS`, `OVERLAY_LINE_OPS`, `OVERLAY_LINE_KINDS`, `OVERLAY_PLAN_TARGETS`, `PROJECT_MACRO_ACTION_TYPES`.

`line_key` = natural composite `"category|sub_category|role_type_id"` for existing lines (matching the live `Forecast` cell key), or a minted stable id (`"new:role:<uuid>"` / `"new:ext:<uuid>"`) for lines added via the overlay.

- `UserMeasurement` — only non-zero cells per `[F-UM-01]`. Full-matrix reconstruction at SAP export time.

### Polymorphism
- **`ChargeableEntity`** uses `entity_type` discriminator (`Project` | `Offering` | `InternalService`); `is_change_or_run` `@property` derives Change/Run from `entity_type` (VIPER §5: Project ⇒ Change, Offering/InternalService ⇒ Run).
- **`Allocation`** uses dual FK pattern (`project_id` for v4 backward compat + `chargeable_entity_id` canonical for Cluster F).

### Versioning
- **Effective-dated header FK** (`DistributionVersion` draft/active with optional `active_from`; `Distribution.version_id` and `RollupCache.version_id` FK into it) — production chain resolved by latest `active_from` ≤ evaluated date; scenario-scoped forks via nullable `scenario_id` (Charging/UM rework FD-3, replaces the v4 row-column `version` String). Mirrors the UMVersion / BTCProfile pattern but adds effective dating; active production versions are immutable, scenario versions stay draft permanently.
- **UM version state machine** (`UMVersion` draft/active, identity `(year, quarter, activated_at)`) — active versions are immutable, never updated in place; re-entry creates a new draft.
- **Sequential per-project** (ForecastVersion.version_number with `UniqueConstraint(project_id, version_number)`) — strict ordering for cycle and CR-approval snapshots.

### Snapshot pattern
- `ProjectSubmissionSnapshot` — PL's original plan + controller-proposed edits.
- `CRSubmissionSnapshot` — CR original + proposed edits for diff.
- `ForecastSnapshot` — total-only capture for forecast-accuracy report.
- `ForecastVersion` — full-grid JSON payload per cycle/CR/manual.
- `ProgressSnapshot` — denormalised milestone + checklist state at cycle completion.

### Cascade rules
- `BTCProfile` → `BTCProfileLine` (`cascade="all, delete-orphan"` on `lines` relationship).
- `ResourceRequest` → `ResourceRequestAssignment` (`cascade="all, delete-orphan"` on `assignments`).
- `ProjectMilestone` → `MilestoneDeliverable` (`cascade="all, delete-orphan"` on `deliverables`; FK also has `ondelete="CASCADE"` at DB level).
- `SavedReport` → `SavedReportShare` (`cascade="all, delete-orphan"` on `shares`).
- `WorkflowTemplate` → `WorkflowStep` → `StepAction` (`cascade="all, delete-orphan"` at each level).
- `BTCProfile.entity_id` FK has `ondelete="CASCADE"` — deleting a ChargeableEntity cascades to its profiles.
- `BTCProfileLine.profile_id` FK has `ondelete="CASCADE"`.
- `BTCProfile.copied_from_profile_id` self-FK has `ondelete="SET NULL"` — preserves descendants when an ancestor profile is deleted.

### Soft delete
`is_active` flag on master-data models (Location, CompetenceCenter, CostCenter, Person, GroupingEntity, GroupingEntityType, GroupingHierarchy, ChargeableEntity, ChargingLocation, LegalEntity, Country, Region, ExternalCostType, MilestoneType, KPIDefinition, WorkflowTemplate, User, DemoPersona via owner). **Never hard-delete** — deactivation preserves audit history and FK integrity.

### Effective-date rate tables
`RateTable` carries `previous_rate` + `previous_effective_date` for one-step historical lookback. Forecast and actuals rate selection happens at compute time in `services/calculations.py`.

### Temporal anchor (dynamic present time / living seed)
VIPER's "today" is **runtime-computed, not a fixed literal**. `config.get_current_period()` returns the real current month (`date.today()` → `YYYY-MM`); `config.DEMO_DATE` is computed once at import as a stable, backward-compatible alias for the many existing reads. The **in-progress current month is locked for forecasting** (it carries partial actuals); the first editable forecast month is `services.calendar.open_forecast_month()` = `DEMO_DATE + 1` (editable iff `month >= open_forecast_month()`). The temporal context is exposed to the frontend via `GET /api/config` → `{current_period, open_forecast_month, fiscal_year}`.

No model column stores the demo date — it is derived everywhere it is read. The committed canonical `seed.sql` is authored against `seed/date_shift.CANONICAL_BASE` (`"2026-04"`) and **date-shifted forward by `month_delta(CANONICAL_BASE, current_period)` months at load and on `/admin/reset-demo`** by `seed/date_shift.shift_sql_dates` (wired in `seed/loader.py`). The shift is a generation-time transform over quoted date/datetime literals (`'YYYY-MM'`, `'YYYY-MM-DD'` with day-of-month clamp, `'YYYY-MM-DD HH:MM:SS'` preserving time); dotted-decimal amounts and prefixed ids never match. All temporal data (actuals/forecasts/baselines `month`, milestone/CR/scenario dates, scheduled-change offsets) moves together so the demo always reflects the present: actuals end at the current month, forecasts open next month, narrative offsets are preserved. `ForecastVersion` rows are re-anchored on `config.DEMO_DATE` with dynamic cycle labels by `loader._seed_forecast_versions()` after the shifted SQL loads.

### Algorithmic WBS
WBS Element is **never stored** per `[F-DM-03]`. Generated by `services/wbs_generator.build_wbs_element` as `<identifier>-64-99-<charging_location_code>`. Subtype prefix is derived from `ChargeableEntity.entity_type` + `identifier`.

### Audit categories
9-category taxonomy (`AUDIT_CATEGORIES`). `_log_audit()` requires keyword-only `category=` parameter at every call site per `[D-CAT-07]`. New audit-emitting code must pick the right category — see column-comment hints on `AuditLog.category` in source.

### Relationship disambiguation via `foreign_keys=`
Several models have multiple FKs targeting the same table — disambiguated via `foreign_keys=[...]` on the relationship:
- `Project.pl` and `Project.current_milestone` (both → `people` and `project_milestones` via different columns).
- `ProjectMilestone.project` (foreign_keys=[project_id]; project also has `current_milestone_id` pointing back).
- `ChangeRequest.submitted_by` / `cc_owner` / `controller` (all → `people`).
- `ProjectDependency.predecessor` / `successor` (both → `projects`).
- `ScheduledChange.created_by` / `reviewed_by` (both → `people`).
- `ScenarioPromotion.promoted_by`, `ScenarioApplyToForecastEvent.applied_by` (→ `people`).
- `CapacityActionLog.acting_user` (→ `people`).
- `BTCProfile.copied_from` (self-ref via `remote_side`).
- `ChargeableEntity.outgoing_edges` / `incoming_edges` (foreign_keys distinguish source vs destination side of `Distribution`).

### Forward-FK with `use_alter=True`
`Project.current_milestone_id` → `project_milestones.id` uses `use_alter=True, name="fk_project_current_milestone"` to break the create_all cycle (Project FKs into ProjectMilestone, ProjectMilestone FKs back into Project). Combined with `post_update=True` on the relationship.
